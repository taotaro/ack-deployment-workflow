# ACK Deployment Workflow and Initializer

The reusable `.github/workflows/deploy-ack.yaml` builds to ACR and deploys caller-owned Kustomize manifests to ACK. The initializer generates a thin caller and application manifests; it does not publish the central workflow or configure GitHub/cloud resources.

## ACK prerequisites and safe preview

Run from an existing target Git repository root containing a Dockerfile. Python 3 and PyYAML are required; Kustomize enables generated-manifest validation. ACK does not require a clean worktree or origin remote, and refuses existing destination files rather than overwriting them.

New onboarding follows the reviewed central `main` branch by default; a SHA is not required or prompted. Central updates are adopted on the application's next new workflow run, not by an automatic redeployment. The example is a local dry-run only:

```bash
bash /path/to/ack-deployment-workflow/init.sh \
  --strategy ack \
  --app fixture-product-app \
  --customer fixture \
  --product product \
  --module app \
  --port 8000 \
  --health /health \
  --environment-map '{"development":{"overlay":"development","environment":"dev"}}' \
  --central-ref main \
  --dry-run \
  --yes
```

`init.sh --strategy ack` delegates to `init-ack.py`; missing application/mapping values are prompted. `--central-ref main` is optional. The mutually exclusive legacy `--central-sha <published-full-SHA>` remains supported for explicit historical pins, rejecting invalid and zero values. Remove `--dry-run` only after review to write files; `--yes` confirms file writes only. ACK never creates a branch, stages files, commits, pushes, opens a PR, changes platform settings, or deploys. Dry-run leaves target files, branch and index unchanged. The app name must equal customer-product-module. Each mapped branch uses `<branch>-env` as its GitHub Environment; overlay and runtime environment are explicit in the mapping.

## ACK generated assets and runtime behavior

```text
.github/workflows/deploy.yaml
deploy/base/{deployment.yaml,kustomization.yaml}
deploy/overlays/<overlay>/kustomization.yaml
docs/deployment.md
```

The generated caller is manual-dispatch only and uses `@main` by default. Main is a moving reference, so centralized changes affect every adopting repository on its next new run; central updates require review and verification, and runtime evidence should record the resolved central SHA. Runtime `__PLACEHOLDER__` tokens remain for central rendering. `--service` and `--hpa` explicitly opt into an HTTP Service and HPA; neither is generated by default. `--config-map <name>` opts into the existing ConfigMap reference. No Ingress, DNS or cloud resources are created.

The central workflow validates inputs and image identity, logs into ACR, builds/pushes, sets ACK context, renders/apply manifests, waits for rollout, attempts Deployment-only `rollout undo` on failure, and logs out. Undo does not revert all resource types and may have no previous revision on first deployment. Lark notification preserves the baseline failure semantics: notification failure can fail the workflow; it is not non-blocking. See generated `docs/deployment.md` for separately required platform configuration and first-deployment authorization.

## Target bundles and migration

Generated callers use `target_routing: environment`. Complete PROD/NONPROD defaults and optional full repository Environment TARGET overrides resolve inside the actual caller Environment job. See [target configuration and migration](TARGET-CONFIG.md) for exact names, fail-closed aliases, explicit Secret mappings and compatibility with published `8e9d563eac561080c4ea9816b00a7e5da4559516`. Services in the same repository/Environment share one target. Local tests do not establish real GitHub precedence or cloud ownership.

## VPS pull (unchanged)

Run `bash /path/to/ack-deployment-workflow/init.sh` for the original interactive strategy selection, or select `--strategy vps-pull`. That path retains its clean-worktree/origin prerequisites and confirmed branch/commit/PR flow. It builds an ACR image for a VPS to pull through Docker Compose; ACK's write-only behavior above does not change VPS pull.
